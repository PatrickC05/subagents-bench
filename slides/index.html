Can background subagents keep a coding agent available?

An orchestrator, background subagents, and a user who keeps asking for things while the work runs

Jonathan Liu · Patrick Chen · October 2026

Notes: Hi, we’re Jonathan and Patrick. Our project asks whether a coding agent that hands work to background subagents can stay available to the user while that work runs: answering, estimating and reprioritizing instead of going quiet until it is done.

Motivation

You don’t ask a collaborator one thing and then go quiet

bug

“Fix the failing test in core.py”

question

“Wait, what does parse_args return?”

status

“How long until the fix is done?”

urgent

“Drop that, prod is broken”

Your coding agent

Busy on the first bug. Everything else waits.

If it can only do one thing at a time and you must wait for it to finish, you aren’t collaborating with it. You are offloading work.

Notes: Here is how people actually use a coding agent. You ask it to fix a bug. You get impatient and ask a question about the code. You ask how long the fix will take. Then something urgent comes up. If the agent can only do one thing at a time and you have to wait for it to finish, you aren't collaborating with it, you're just offloading work. That is the experience we want to measure and improve.

Notes: What do subagents buy in prior work? Anthropic's research system, a lead agent with parallel subagents, beat a single agent by about 90 percent on their research evaluation, but used about fifteen times the tokens of a chat, and they note it suits parallel work more than coding. LLMCompiler runs function calls in parallel and cuts latency up to 3.7 times. Alpha-UMi splits an agent into smaller specialists. And Cemri et al. catalogue how multi-agent systems fail, mostly in coordination. All of these ask whether subagents make the answer better or faster. We ask whether they keep the agent available.

Hypothesis

Handing work to background subagents keeps the orchestrator free, and that improves interactivity

If it holds

  • New requests get a reply sooner
  • Earlier work keeps going
  • Estimates and priorities are handled while work runs

What could break it

  • The orchestrator’s own thinking is the bottleneck
  • Coordinating subagents adds overhead
  • Delegated work is done worse

Notes: So our hypothesis: if the orchestrator hands work to subagents that run in the background, it stays free to talk to the user, and interactivity improves. If that holds, requests get replies sooner, earlier work keeps going, and the agent can give estimates and reprioritize while work runs. It could fail if the orchestrator's own thinking is the bottleneck, if coordinating subagents costs more than it saves, or if delegated work is done worse.

Notes: First result. When every request is a bug, delegating does not make the agent more responsive. In the arrival-rate experiment, 24 sessions, the single agent received new bugs in about 20 seconds against about 40 for the background manager, touched the files twice as fast, fixed slightly more bugs, and cost a third as much. Sending bugs faster hurt the manager more, not less. The smokes agreed: background managers beat blocking managers, but neither beat the single agent.

Appendix · pilot: why

Requests wait behind the model’s thinking, not behind its commands

86–98%

of bugs that found the orchestrator busy arrived during one of its model calls

0.3 s

median length of the single agent’s own commands (25 s at most), even when told to test every fix

4.5 min

longest single DeepSeek call in the smoke, about 21k reasoning tokens

Managing subagents makes the orchestrator’s own calls longer, so offloading the commands buys nothing here.

Notes: Why does delegation lose? Because the waiting isn’t where we expected. Almost every bug that found the orchestrator busy arrived while it was thinking, in a model call, not while it was running a command. The single agent’s commands are tiny, a third of a second at the median, even when we required it to test each fix. And single calls can be huge: one DeepSeek call reasoned for about 21 thousand tokens over four and a half minutes. A manager coordinating subagents thinks longer per call, so moving the commands elsewhere doesn’t help.

Notes: Then we changed what the user asks for. Between bugs, the user now asks questions about the code, checks status, and sometimes marks a bug urgent. Now the picture flips. The single agent answered only 56 percent of questions, with a median of almost five minutes. Both subagent conditions answered 81 percent within about a minute, and status checks in 42 seconds, while fixing the same number of bugs or more. And interestingly, once questions arrive, the orchestrator with all tools starts delegating by itself. Four sessions per condition, so these are directions.
