Can small subagents keep a big agent available?

A large orchestrator, small background workers, and a user who keeps asking for things while the work runs

Jonathan Liu · Patrick Chen · October 2026

Notes: Hi, we’re Jonathan and Patrick. Our project asks whether a large model that hands work to small subagents can stay available to the user while that work runs. We started from a different question, delegation for accuracy, and the results pushed us toward interactivity. I’ll walk through that path in about ten minutes.

Motivation

One chat, many requests, not all about the same task

Agent thinking and running commands on bug 1

New messages wait

A coding agent reads new messages only between its own steps. While it works, the user waits.

Notes: Picture how people actually use coding agents. You ask for a fix, and two minutes later you ask a question about the code, then you ask when the fix will land, then something urgent comes up. These requests are related, the same repository, but they are not the same task. An agent reads a new message only between its own steps, so while it is thinking or running a command, everything else waits. That is the user experience problem we care about.

The claim we test

Handing work to background subagents keeps the orchestrator free to answer the user

If it holds

  • New requests are read and answered sooner
  • Earlier work keeps going
  • Bugs still get fixed, at a cost we can name

Closest work

Gaia2 (Froger et al., ICLR 2026): environments that change on their own, with time limits; GPT-5 (high) leads at 42% but fails time-sensitive tasks.

AsyncTool: delayed tool feedback hurts agents; those that coordinate task switching do better.

We differ: a coding agent’s availability to the user while its own work runs, whether delegating to small subagents buys it, and whether it can say when each fix will be ready.

Gaia2: arxiv.org/abs/2602.11964

Notes: The claim is simple. If the orchestrator hands work to subagents that run in the background, it should stay free to read and answer the user. If that holds, new requests get answered sooner, the earlier work keeps going, and we still fix bugs. The closest work is Gaia2, from Meta at ICLR 2026, which benchmarks agents in environments that change on their own under time limits; even the best model, GPT-5 on high, fails the time-sensitive tasks. AsyncTool shows delayed tool feedback hurts agents. We differ in focus: we care about availability to the user and to requests that are not known yet, and whether the agent can predict when its work will be done.

Setup

A large orchestrator with small subagents, on real repositories

Models

Orchestrator: DeepSeek-V4.1-Flash

Subagents: Gemma-4-31B, up to 3 at once

Both served by Sail; we log raw tokens and timings

Harness

Our own agent loop inside harbor + Docker

Tools: bash, edit, read, list, search, and spawn_subagents

Benchmark

SWE-sweep: whole repositories with 6–14 hidden bugs

Each bug graded separately, so each can be its own request

Conditions: single agent · all-tools orchestrator that may delegate · manager that can only read, so every edit and test goes to a subagent · blocking or background spawns

Notes: Our setup: DeepSeek V4.1 Flash is the orchestrator, Gemma 4 31B is the subagent, up to three at a time, both on Sail. We wrote our own agent loop running inside harbor and Docker. The benchmark is SWE-sweep, where each task is a whole repository with several hidden bugs that are graded one by one. That matters because each bug can become its own user request. We compare a single agent, an orchestrator with all tools that may delegate, and a manager that can only read, so it must delegate, with spawns that either block or run in the background.

First try: delegation for accuracy

Given one task and 5 steps, delegation either never happened or never helped

Whether it delegates follows the task, not the prompt. And small subagents did not add accuracy. So we asked what else they could add: availability.

Notes: We first tried the usual question: does delegating to small models improve accuracy? On Terminal-Bench, the orchestrator with its own tools almost never delegated, zero of 64 episodes, and even when we told it its steps were scarce it said the task was simple and did it itself. On SWE-sweep, where the whole repository is the task, it delegated every time, but no bug was fixed: the small subagents spent their steps reading code. So uptake follows the task, and small subagents didn’t buy accuracy. That pushed us to a different benefit: keeping the agent available.

Notes: So we built timed sessions on SWE-sweep. A simulated user sends a bug every few minutes, each one pointing at the files and a hidden test, and says keep working on the earlier ones. Later we added questions about the code, status checks and urgent bugs. For every request we measure how long until the orchestrator received it and answered it, how long until anyone touched or edited the relevant files, and in the end whether the bug was fixed, the answer correct, and the estimate accurate.

Notes: First result. When every request is a bug, delegating does not make the agent more responsive. In the arrival-rate experiment, 24 sessions, the single agent received new bugs in about 20 seconds against about 40 for the background manager, touched the files twice as fast, fixed slightly more bugs, and cost a third as much. Sending bugs faster hurt the manager more, not less. The smokes agreed: background managers beat blocking managers, but neither beat the single agent.

Why

Requests wait behind the model’s thinking, not behind its commands

86–98%

of bugs that found the orchestrator busy arrived during one of its model calls

0.3 s

median length of the single agent’s own commands (25 s at most), even when told to test every fix

4.5 min

longest single DeepSeek call in the smoke, about 21k reasoning tokens

Managing subagents makes the orchestrator’s own calls longer, so offloading the commands buys nothing here.

Notes: Why does delegation lose? Because the waiting isn’t where we expected. Almost every bug that found the orchestrator busy arrived while it was thinking, in a model call, not while it was running a command. The single agent’s commands are tiny, a third of a second at the median, even when we required it to test each fix. And single calls can be huge: one DeepSeek call reasoned for about 21 thousand tokens over four and a half minutes. A manager coordinating subagents thinks longer per call, so moving the commands elsewhere doesn’t help.

Notes: Then we changed what the user asks for. Between bugs, the user now asks questions about the code, checks status, and sometimes marks a bug urgent. Now the picture flips. The single agent answered only 56 percent of questions, with a median of almost five minutes. Both subagent conditions answered 81 percent within about a minute, and status checks in 42 seconds, while fixing the same number of bugs or more. And interestingly, once questions arrive, the orchestrator with all tools starts delegating by itself. Four sessions per condition, so these are directions.

Notes: Here is what that looks like in a transcript. The single agent clearly intends to answer. Its reasoning says “let me answer number nine quickly”, often with the answer already worked out, and then it runs another ten to fifty-seven steps on its bugs without ever calling reply. In one click session its last reply came at two minutes forty-seven seconds into a thirty-minute session. Nothing blocks it; it just doesn’t switch.

Takeaways and next steps

What we learned

  • Small subagents didn’t add accuracy, and on bug fixing alone doing it yourself is faster and cheaper
  • The wait is the big model’s thinking, not its tools
  • With mixed requests, subagents keep the agent available: 81% vs 56% of questions answered, about 5× faster

Next

  • Accurate timing: only 21–38% of bugs got an estimate
  • Steering and priorities: urgent bugs, changed plans
  • More rounds; workloads with slow commands; a faster orchestrator

Caveats: 4–12 sessions per condition; Sail latency varies; amd64 emulation on one Mac; manager subagents broke passing tests in 5 of 16 bugs-only sessions

Notes: To sum up. Small subagents didn’t buy accuracy, and when the user only sends bugs, doing the work yourself is faster and cheaper, because the waiting comes from the big model’s thinking. But when the user also asks questions and checks status, background subagents keep the agent available: far more questions answered, about five times faster, at the same fix rate. Next we want to measure timing, since agents rarely give estimates and miss them, and steering, plus more rounds and harder workloads. The caveats are small samples, provider latency, and emulation.
